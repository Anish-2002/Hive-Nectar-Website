# 00 — Hive Nectar admin CRM: plan and capability matrix

**Decision (13 Oct 2026, user):** administration is replaced by an **own CRM built inside the existing
app**, covering the full scope originally given. **The admin-plane security hardening applied to
production stays** — it is independent of the CRM build and already verified live.

## 1. Why this architecture

- **Live data.** Reads and writes go straight to Supabase through gated RPCs — no mirror, no sync,
  no record cap.
- **Cloud-hosted** with the site; works from any browser, any device.
- **No member data leaves Supabase.**
- **One identity system**: the existing Supabase login plus the `is_admin` check.
- **Reachable anywhere you can log in.**
- **No bridge, allowlist or audit table to build** — the gated RPCs already exist.

## 2. Non-negotiable architecture rules (learned the hard way)

1. **Admin UI talks to Supabase through `SECURITY DEFINER` RPCs only.** Never `.from()` in an admin page —
   RLS returns only the caller's own row, so direct table access silently "works" for some tables and
   silently fails for others.
2. **Every RPC is gated** by the existing `is_admin()` / `admin_ok()` check, and returns **`jsonb`**
   (PostgREST 400s on `TABLE` returns).
3. **Every deploy file ends with** `NOTIFY pgrst, 'reload schema';` or the API serves a stale schema.
4. **No privilege in the browser.** The anon key stays the only key in client code; never `service_role`.
5. **Member-facing behaviour is untouched.** No member page, game rule, reward, subscription or record
   semantics change. If a capability needs such a change, stop and ask.
6. **No emoji, no AI-look** in UI or generated content.

All but 13 still carry the house default `PUBLIC` EXECUTE, so an anon caller can *reach* the
function and is then stopped by the `admin_ok()` guard (`{"error":"Forbidden"}`). Revoking
`PUBLIC` on those 41 is a tidy-up, not a fix — the SQL is in `04-ADMIN-UI-BUILD.md`.

## 5. Build phases

- **P1 — Admin app shell.** A real route in the React app: admin gate via `admin_ok()`, navigation,
  loading/error states, and the existing RPCs wired up. Immediately covers Members, Tasks, Themes, Tokens,
  Milestones, Config, Collaboration, Logs.
- **P2 — Communications + Support.** New gated RPCs over `communications` and `contact_inquiries`
  (assign / status / respond / resolve). This is what retires `admin_comms.html` and `admin_inbox.html`.
- **P3 — Badges, challenges, impact factors.** New gated RPCs over `badges`, `badge_stages`,
  `challenges`, `impact_conversion`, plus the point-adjustment audit trail.
- **P4 — Subscriptions.** Read surface first (tier, status, renewal, failures, cancellations) from
  `subscriptions` / `stripe_events`. **Billing actions are a separate, approval-gated step**: they need an
  edge function holding the Stripe secret, and no such secret exists in the repository.
- **P5 — Analytics.** Aggregate read RPCs (growth, task completion, theme performance, nectar
  distribution, retention, revenue). Aggregation must happen server-side in SQL — never by pulling rows.
- **P6 — Administrator management.** Roles + permissions, email invitations (needs working SMTP/Brevo and
  a deployed edge function — `send-email` currently returns 404), invitation status, revocation, audit.
- **P7 — Automation.** Triggered and scheduled actions, hosted where they can run 24/7.
- **P8 — Retire the legacy admin pages** into `information/legacy-admin/` once replaced, and verify the
  full path end-to-end in a browser.

## 6. Open risk that must be handled before P2/P3

Five tables have **row level security switched off entirely** and were proven writable with the public
anon key: `achievements`, `challenges`, `impact_conversion`, `task_sigma_logs`, `theme_stats`.

Turning RLS **on** is the correct fix, but it can only be done after checking whether any member page writes
those tables directly with the anon key — if it does, enabling RLS without policies would break
member-facing behaviour, which the contract forbids. So: **inspect the site's write paths to those five
tables first, then apply the smallest change that closes the hole without touching member behaviour.**

## 7. Next action (remaining scope)

P1, P2, P4, P5 and the P8 content half are **built and verified**; the admin surface is
`/admin` and all 54 live RPCs are wired. What is left:

1. **P3 — gamification:** gated CRUD over `badges`, `badge_stages`, `challenges`,
   `impact_conversion`, plus the point-adjustment audit trail. These four tables are also the
   ones with RLS **off** (§6), so this phase should close that hole at the same time.
2. **P6 — administrator management:** roles, email invitations and invitation status. Email
   needs working SMTP plus a deployed edge function (`send-email` currently 404s).
3. **Support workflow columns** (assignee, response, resolution) — a small additive change.
4. **P7 — automation:** scheduled and triggered actions, hosted where they can run 24/7.

Every one of these is additive: a new gated `jsonb` RPC following §2's rules, ending in
`NOTIFY pgrst, 'reload schema';`, deployable by hand in the Supabase SQL editor.
